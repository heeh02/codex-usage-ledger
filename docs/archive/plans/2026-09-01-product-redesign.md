# Codex Usage Ledger 专业化重构方案

> 已归档的历史方案，不是当前执行权威。当前协作目标见仓库根目录
> [`goal.md`](../../../goal.md)，统计规则见
> [统计契约](../../contracts/accounting.md)。

状态：**Goal 执行基线 / v1.0**
制定日期：2026-09-01（Asia/Shanghai）
适用范围：Rust 本地账本、Codex 官方账号用量同步、React 仪表盘、macOS 菜单栏与窗口应用

## 1. 决策摘要

Codex Usage Ledger 不再被定义成一个“把所有 Token 加起来的看板”，而是一个同时回答四类不同问题、并明确证据边界的本地用量观测产品：

1. **账号实际用了多少**：以 Codex 官方账号日桶和累计值为主账。
2. **本机哪些工作产生了用量**：以 replay-safe 的本机 sampling 事件归因到项目、模型、Session 和 Subagent。
3. **这些结论有多可信**：逐账号、逐日期展示覆盖、延迟、未匹配和未知状态。
4. **尚未捕获的账号至少解释了多少本机活动**：以两个已校准账号的逐日官方桶为上界，提取本机历史错归产生的正残差，只给出缺失账号合计下限。

本轮重构的首要目标不是继续增加卡片，而是确保用户能够在不阅读说明文档的情况下回答四个问题：

- 这个数字是什么？
- 它来自官方还是本机？
- 它覆盖哪个账号、设备和时间窗口？
- 它是精确值、下限、本机样本，还是未知值？

## 2. 研究与盲测依据

### 2.1 独立首次用户盲测

盲测使用不继承历史上下文的独立模型，只告知产品用途；测试者只能操作可见 GUI，不能读取代码、数据库、日志或既有结论，也不能执行导出、删除或账号切换。

盲测确认以下主路径已经可发现：

- 时间段、账号、项目、模型和粒度筛选；
- 项目下钻到 Session 与 Subagent；
- Session 自身用量与子树用量；
- 项目周/月/至今排行；
- 总量、组成、项目比较和趋势图；
- 窄窗口下的基本响应式布局。

盲测同时识别出六项高优先级理解障碍：

1. 主 KPI 在官方总量、本机归因和下限之间切换语义。
2. 顶部时间周期与左侧排行周期相互独立，但作用域不清楚。
3. 进入项目或 Session 后，没有持续重申确切时间窗口。
4. 全部账号视图混合了官方已覆盖账号和仅有本机下限的账号。
5. 匹配率、未匹配、UNKNOWN 和 QUARANTINED 的关系与分母不清楚。
6. 项目占比分母、Top-N 剩余量和本机样本相对账号总量的关系不清楚。

其他易用性问题包括模型无法继续下钻、Session 长标题影响扫描、中英文与缩写混用，以及 Token 趋势容易被误解为开发强度。

安装版 v15 的二次无上下文盲测、实测失败路径、已完成修复与剩余门禁见
[`blind-usability.md`](../../releases/v0.1.0/blind-usability.md)。
安装版性能、真实额度接线、数据库恢复与自动化门禁的证据见
[`verification-v16.md`](../../releases/v0.1.0/verification-v16.md)。

### 2.2 当前实现审计

当前架构已经建立正确的基础边界：

- 官方 `account/usage/read` 用于账号级 Total；
- 本机 post-sampling 匹配用于项目、模型、Session 和 Subagent 归因；
- 不汇总 `state_5.sqlite.threads.tokens_used`；
- 使用 SQLite/log 与 rollout 游标进行增量采集；
- 通过 event identity 和累计计数器差分避免 fork/replay 重复计数。

当前主要风险集中在语义层和多账号覆盖层：

- 一个全局 `coverageStart/coverageThrough` 无法表达多个账号不同的官方覆盖日期；
- “官方账号档案齐全”不等于“所选日期每个账号都完整覆盖”；
- 请求条数匹配率不能替代 Token 数量覆盖率；
- 无法计算的 Token 数量不应显示为 0；
- 官方账号总量可能包含其他设备，本机项目样本只能解释当前设备；
- 顶部筛选与侧栏排行使用两个独立周期状态；
- “本周”和“本月”隐藏确切边界，跨月周容易被误判为算法错误。

例如 2026-09-01 的自然周从 2026-08-31 开始，因此本周可以大于本月。这是合法集合关系，但当前界面没有显示 `8/31—9/1 · 跨月`，属于表达失败。

## 3. 不可破坏的数据原则

### 3.1 双账本原则

| 数据视图 | 权威范围 | 不允许承担的职责 |
| --- | --- | --- |
| 官方账号账本 | 账号 Total、官方日桶、累计值、额度池 | 不推断项目、模型、Session 或 Token 组成 |
| 本机归因账本 | 项目、模型、Session、Subagent、输入/缓存输入/输出/Reasoning | 不冒充完整账号总量，不代表其他设备 |
| 未捕获账号残差估算 | 已捕获账号逐日官方上界无法解释的本机正残差；缺失账号合计的保守下限 | 不拆分未知账号，不并入官方或本机确认总量，不把全局差额当项目事实 |

官方与本机账本可以并排比较，但只有账号、日期和覆盖条件一致时才允许计算差额。禁止把“全部官方 − 全部本机”的全局差额分摊成项目；唯一允许的估算是逐账号逐日的正残差，并且只能按该格内已经观察到的 Token 组成做守恒分配。

### 3.2 Token 算术

```text
uncached_input = max(input - cache_read - cache_write, 0)
cache_read = cached_input
cache_write = cache_write_input
total = input + output
reasoning 是 output 的明细，不再次加入 total
```

默认组成图只使用四个互斥桶：输入（非缓存）、缓存读取、缓存写入、输出；四者之和必须等于本机样本 Total。Reasoning 作为输出的明细另列。官方仅提供 Total 时，不得按本机比例放大组成，也不得把本机组成与官方 Total 放在同一分母下绘制百分比。

缓存写入字段具有独立覆盖率。旧日志没有该字段时，其未拆分输入暂留在“输入（非缓存）”并显示覆盖不足，不能显示成已知的零写入。顶部账号 KPI 不再展示本机缓存命中率；改为展示“本机组成样本”，避免用户把全设备官方 Total 与本机缓存读取量误认为同一总体。

### 3.3 未知值

- `0` 表示已知的零。
- `null / —` 表示无法测量或无覆盖。
- `lower_bound` 表示已证实至少为该值。
- `local_sample` 表示只覆盖本机可归因样本。

任何未知 Token 数量都不得以 0 参与求和、占比、均值或趋势。

### 3.4 时间窗口

每个窗口必须保存并展示：

```text
window_start
window_end
timezone
calendar_or_rolling
partial
crosses_month
comparison_start
comparison_end
```

只有当窗口 A 是窗口 B 的真实子集时，才允许检查 `A <= B`。不能根据“周”“月”文字推断包含关系。

## 4. 统一指标合同

所有主指标通过一个稳定的数据对象暴露：

```text
ResolvedMetric {
  value: u64 | null
  source: official | local | reconciled
  status: exact | lower_bound | local_sample | unknown
  window_start
  window_end
  timezone
  account_scope
  machine_scope
  coverage
  definition_id
}
```

UI 组件不得根据筛选条件悄悄改变同一指标的定义。选择项目或模型后，账号 Total 卡片仍是账号 Total；项目筛选只影响“本机归因”区域。

### 4.1 推荐 KPI

主结果指标：

- **账号 Total**：官方精确值或明确标记的逐账号下限。
- **本机可归因 Total**：当前设备确认事件的 Total。
- **归因可解释度**：本机可归因量相对同范围账号账本的比率；范围不可比时不展示。

诊断驱动指标：

- sampling 请求数；
- 活跃 Session 数；
- 非缓存输入；
- 输出；
- Subagent 启动数；
- 最近活动时间。

质量护栏：

- 缺少官方档案的账号数；
- 逐账号日期覆盖；
- 未匹配请求数与请求匹配率；
- Token 覆盖率（仅在分子分母可证实时展示）；
- UNKNOWN/QUARANTINED 事件；
- 官方同步延迟与本机水位延迟。

## 5. 多账号与多设备对账

### 5.1 对账粒度

基础对账粒度为：

```text
account × local_day × machine
```

每个账号每天独立确定状态：

- `EXACT_OFFICIAL`：该账号该日有完整官方桶；
- `LOCAL_TAIL`：官方覆盖之后的本机已确认增量；
- `LOCAL_ONLY_ACCOUNT`：已识别账号但尚无官方档案；
- `UNKNOWN`：账号、日期或登录间隙无法证明归属。

全部账号结果逐账号逐日求和。只有所有被观察账号在整个所选窗口都为 `EXACT_OFFICIAL`，整体才是 `exact`。

### 5.2 覆盖字段

不再使用一个容易误导的全局覆盖日期替代多账号状态。API 至少返回：

- 每个账号的 `coverageStart` 和 `coverageThrough`；
- `commonCoverageStart/commonCoverageThrough`：所有账号共同覆盖的交集；
- `latestCoverageThrough`：任一账号最新覆盖日期，仅用于新鲜度；
- `missingOfficialAccountCount`；
- `observedAccountCount`：账本实际捕获到的稳定或临时身份数；
- `userConfirmedAccountCount`：用户确认曾使用过的账号总数，只作为完整性目标；
- `unobservedAccountCount`：用户确认但尚未捕获身份的账号数，不生成占位 Token；
- 当前窗口逐日覆盖状态。

### 5.3 登录切换

- 账号切换关闭前一个 auth epoch，开启新 epoch；
- OAuth 等待、登出和无法识别区间保持未归属；
- 当前 `auth.json` 不能反向认领全部历史；
- 历史 workspace 只有在再次被官方身份观察时才能合并；
- 用户可以校准曾使用账号总数；例如用户确认 4 个、账本只捕获 2 个时，界面显示 `2/4` 并保持“全部账号”为下限；允许显示缺失两个账号**合计**的逐日残差下限，但不生成两个虚构身份，也不声称能够拆分各自 Token；
- 套餐类型（如 Pro、Plus）只取自对应身份登录时捕获的官方 `plan_type`，用户口述套餐不反向绑定到未知身份；
- 合并前后事件数和每个 Token 维度总量必须守恒。

### 5.4 多设备

- 官方账号 Total 跨设备，只能按账号去重；
- 本机归因始终带 `machine_id`；
- 多台设备的本机账本只有在事件键可证明唯一时才能合并；
- “账号总量 - 当前 Mac 归因”不是未归因项目，而是范围差异。

### 5.5 未捕获账号合计估算

第一阶段成功标准不是等待四个账号全部重新登录，而是先严谨校准两个已捕获账号，并回答“剩余两个账号合计至少对应了多少本机活动”。算法冻结为：

```text
for each captured account × local day with official coverage:
    residual = max(local attributed Total - official daily Total, 0)
missing accounts combined floor = sum(residual)
```

只在同一账号、同一自然日、同一时区中比较。官方缺日不按零处理；官方大于本机时不产生负抵扣，因此一个账号较大的官方值不能遮盖另一个账号的历史错归。正残差按该账号日内部的项目、模型与四个不重叠 Token 成分（cached、uncached、reasoning、other output）使用最大余数法精确分配。

API 必须同时返回：

- `definitionId=missing_accounts_residual_v1`；
- `status=conservative_floor`；
- 缺失账号合计数、`canSplitByMissingAccount=false`；
- 对齐账号日、正残差账号日、排除账号日与覆盖起止；
- 原始残差、组成不变量偏差、分配舍入差；
- 总量与当前项目/模型筛选量；
- 按日、项目、模型以及来源已捕获账号的审计明细。

验收要求是所有 Token 维度逐级守恒、项目和模型之和等于估算总量、单项目筛选不改变估算母集、选中单个已捕获账号时该估算不适用。未来捕获第三或第四账号后，算法自动缩小缺失账号集合并重算，不改写既有本机事实。

## 6. 可持续增量架构

现有增量方向保留并强化：

1. `logs_2.sqlite` 按稳定 log id 游标读取；
2. rollout 按文件 identity + byte offset 游标读取；
3. post-sampling 记录与相邻 `last_token_usage` 一对一匹配；
4. 原始事件保留短周期，旧事件压缩到日汇总；
5. replay key 永久或长期保留，旧文件重现也不会重复入账；
6. 官方日桶使用 upsert，允许后端修订历史日期；
7. 每次启动只做 cursor resume、schema/version 检查和未完成事务恢复，不重新全量回填；
8. 只有用户显式选择“重建账本”时才运行全历史校验。

删除 Codex 项目或 Subagent 后：

- 已经进入本应用账本的不可变事件与日汇总继续保留；
- Codex 当前会话索引只影响目录和标题，不删除历史用量；
- 从未被本应用采集且已被 Codex 删除的逐 turn 明细无法恢复，标记为历史覆盖缺口；
- 不使用累积 `tokens_used` 填补缺口。

## 7. 信息架构

### 7.1 总览

总览固定分为三层，不能混合：

#### A. 账号用量

- 账号 Total；
- 官方已入账；
- 本机尾部下限；
- 缺档账号本机下限；
- 逐账号覆盖矩阵；
- 官方同步时间。

#### B. 本机归因

- 本机可归因 Total；
- 输入、缓存输入、非缓存输入、输出、Reasoning；
- 项目、模型、Session、Subagent；
- sampling 请求与活跃会话。

#### C. 数据质量

- 官方账号完整度；
- 日期覆盖；
- 请求匹配率；
- 未匹配、UNKNOWN、QUARANTINED；
- 本机与官方新鲜度。

#### D. 未捕获账号合计估算

- 保守下限总量与精确覆盖日期；
- 输入、缓存输入、非缓存输入、输出、Reasoning 组成；
- 按日残差曲线；
- 项目和模型排行；
- 明确的“两个账号合计、不可拆分、不得并入主账”说明。

### 7.2 筛选作用域

全局筛选只保留：

- 账号；
- 时间窗口。

项目、模型和 Session 属于本机归因区域的局部筛选。粒度属于趋势图局部控制。任何局部筛选都必须靠近它影响的组件。

### 7.3 左侧项目栏

左侧是导航与项目活跃度，不再伪装成账号总账：

- 标题明确为 `本机项目归因`；
- 展示确切周期，例如 `本周 · 8/31—9/1 · 跨月`；
- 周/月/至今使用完整中文；
- 默认按所选周期本机 Token 排序；
- 可切换增长、最近活跃、15 分钟活动和 Session 数；
- 项目百分比以本机项目样本为唯一默认分母；
- 总览必须显示守恒式：`具体项目 + 本机未归属 + 无项目证据 = 账号 Total`；
- 同屏显示“项目归因覆盖率”和差额瀑布。差额至少区分官方早于本机证据、官方有量但本机无采样证据的日期、其余净差；三者之和必须精确等于账号 Total 减本机可归因 Total；
- 官方账号窗口与本机证据窗口分别标注，不用一个起止日期冒充共同覆盖；
- 无项目证据部分禁止按现有项目比例分摊，只有未来发现新的原始 sampling 证据后才能重新归因；
- Top-N 必须显示“其他项目”或完整展开。

顶部账号时间范围与侧栏周期可以独立，但必须显式标记为两个作用域；首选方案是提供“跟随总览”模式作为默认值。

### 7.4 项目页

顶部固定显示：

```text
项目名
本机归因 · 8/31 00:00—9/1 当前 · 跨月
Total / 输入 / 缓存读取 / 缓存写入 / 输出 / Reasoning（输出内）
```

主体包含：

- 项目 Token 活动曲线；
- 组成趋势；
- 模型排行并可下钻；
- Session 列表；
- Subagent 树；
- 项目覆盖和最后活动。

### 7.5 Session 与 Subagent

Session 表使用稳定列：

```text
标题 | 模型 | 自身用量 | 子树用量 | 直接子代理 | 更新时间
```

长标题截断并悬停查看全文。详情页持续显示项目面包屑、账号范围和日期窗口。`ownUsage` 与 `treeUsage` 永远并列命名，避免把子树累计误认成新调用。

### 7.6 账号页

账号页先展示覆盖矩阵，再展示每个账号：

```text
账号 | 官方已入账 | 本机尾部 | 本机独有 | 覆盖截至 | 状态
```

额度池单独作为 Quota 层，不能与 Token 账本的 Total 或组成混为一谈。

## 8. 趋势与“开发强度”

Token 量反映模型处理活动，不等同于有效开发产出。趋势区分为：

### 8.1 Token 活动

- Total；
- 输入 / 缓存读取 / 缓存写入 / 输出；
- 模型；
- 项目；
- 官方账号日桶与本机归因分别绘制。

### 8.2 工作活动

- sampling 请求数；
- 活跃 Session；
- Subagent 启动数；
- 活跃分钟；
- 非缓存输入；
- 输出。

这些原子指标以 small multiples 展示，优先于生成一个不可解释的“开发强度分”。若后续加入综合指数，必须公开公式、权重、单位、边界和版本。

比较规则：

- 自然周期与相同已流逝长度的上一自然周期比较；
- 滚动周期与前一个等长滚动窗口比较；
- 覆盖不完整时不显示负增长结论；
- 图例明确区分官方账号 Total、本机归因和上一周期；
- 未覆盖区域使用阴影，不画成零线。

## 9. GUI 与可用性规范

- 遵循 Codex 的系统字体、黑白灰主色、细边框和克制状态色；
- 默认窗口尽量一屏呈现核心信息，次级内容用标签页和下钻；
- 支持 `⌘+`、`⌘−`、`⌘0`，缩放后仍保持可读与无横向溢出；
- 正文字号不小于 12px，核心数据与标题保持有限层级；
- 同一语义使用统一中文；专业术语可保留英文但不使用未解释的单字母缩写；
- 刷新按钮保持固定宽度，加载状态不改变布局；
- 后台增量同步不反复显示“正在回填历史”；
- 只有首次迁移或用户触发重建才显示历史回填进度；
- 支持键盘焦点、VoiceOver 标签、减少动态效果和足够对比度；
- 隐私模式隐藏账号标签、项目名、Session 标题和绝对路径，不改变计算结果。

## 10. 实施阶段

### P0：指标语义与时间窗口

交付：

- `ResolvedMetric` 与统一状态枚举；
- 确切时间范围、跨月和部分周期字段；
- 未知值 nullable；
- 主 KPI 不因项目/模型筛选改变语义；
- 顶部与侧栏作用域显式化；
- 回归测试覆盖跨月周、月初、年界和空覆盖。

退出门槛：任何主数字都能回答来源、范围、状态和定义。

### P1：逐账号逐日对账

交付：

- account × day 覆盖状态；
- common/latest coverage；
- 全部账号逐日求和；
- auth epoch 与切号状态；
- 官方迟到/修订后的确定性重算；
- 多账号差异覆盖测试。

退出门槛：同口径下全部账号不会小于任一单账号；缺档时不会标记精确。

### P2：本机归因与增量生命周期

交付：

- 启动 cursor resume；
- 首次迁移与日常增量状态分离；
- compaction/replay 守恒测试；
- 删除 Codex 会话后的历史账本保留；
- 存储体积、保留策略和可恢复事务。

退出门槛：重启、重复文件、游标回退和官方修订均不重复计数。

### P3：信息架构与可视化

交付：

- 总览三层结构；
- 账号覆盖矩阵；
- 项目页、模型下钻、Session/Subagent 表；
- Token 活动与工作活动曲线；
- 项目分母和“其他项目”；
- 统一语言、响应式和缩放。

退出门槛：首次用户无需解释即可区分账号总量与本机归因。

### P4：质量与发布候选版

交付：

- 自动化不变量测试；
- 性能、数据库迁移和故障恢复测试；
- 可访问性与窄窗口验证；
- 独立无上下文盲测；
- 开源文档、隐私说明、已知限制和发布清单。

退出门槛：盲测者能够正确解释主要数字、时间范围、来源和精确性。

### P3.5：逐账号官方额度周期

交付：

- 账号 × limit id × 官方窗口的周期档案；
- 官方周窗口、短窗口和未知动态窗口分层；
- 周期内本机输入/缓存读取/缓存写入/输出/Total 样本与缓存写入字段覆盖率；
- 切号后的独立账号快照与周期继续；
- 计划到期重置和观察到的官方提前重置；
- Bank Reset、Tibo 等外部触发只标为“来源无法证明”，不猜测归因；
- 百分比与 Token 的经验相关性明确不是固定换算。

退出门槛：用户可以独立回答每个账号当前处于哪个官方额度周期、用了多少百分比、本机同期观察了多少 Token、何时计划重置，以及是否观察到提前重置。

## 11. 必须自动化的不变量

1. `total = input + output`；缓存不重复加入。
2. Reasoning 不重复加入 Total。
3. 同一事件键最多入账一次。
4. 项目归因合计等于同范围本机确认样本。
5. 账号重建前后事件数和全部 Token 维度守恒。
6. 全部账号值不小于同口径任一包含账号；状态必须兼容。
7. 未知 Token 为 null，不能作为零求和。
8. 只有真实包含窗口才执行单调性校验。
9. 2026-09-01 场景允许本周大于本月，并显示跨月。
10. 两个账号官方覆盖日期不同时，全部账号不标记为精确。
11. 切号发生在一天中间时，事件按 epoch 归属，无法证明的间隙保持未知。
12. 官方日桶迟到或修订后替换对应桶，不与旧值相加。
13. 多设备官方 Total 不重复，本机归因保留机器维度。
14. 删除当前 Codex 会话索引不会删除已入账历史用量。
15. 切换任一筛选不会改变未受影响指标的定义。

## 12. 产品成功标准

产品正确性：

- 已知重复计数路径为零；
- 主指标 100% 携带来源、时间范围和状态；
- 数据质量页能解释所有不精确主指标；
- 多账号、跨月、切号和官方迟到测试全部通过。

可用性：

- 首次用户能在 30 秒内找到某项目本周和本月 Token；
- 首次用户能解释账号 Total 与本机项目合计为何不同；
- 首次用户能找到 Session 自身与 Subagent 子树用量；
- 首次用户不会把最近 15 分钟 Token 速率理解为额度消耗速度；
- 关键操作在默认窗口和 80%–150% 缩放下无需横向滚动。

性能：

- 日常启动不全量扫描历史；
- 无新增数据时增量轮询接近常量成本；
- 大历史数据通过日汇总和 replay key 控制体积；
- 刷新与后台同步不阻塞 UI 主线程。

## 13. 明确不做

- 不根据 API 单价估算费用，除非以后独立增加并明确版本化的价格层；
- 不读取、复制或保存 OAuth token；
- 不自动切换 Codex 账号；
- 不使用 IP 推断账号；
- 不把缺失官方数据按比例分配给项目；
- 不恢复已经删除且从未被账本采集的逐 turn 明细；
- 不把 Token 量直接宣称为有效产出或开发质量。

## 14. 执行顺序与变更控制

每个阶段遵循：

```text
先写失败测试和指标定义
→ 实现最小语义改动
→ 对账不变量
→ API 契约
→ GUI 呈现
→ 真实数据快照检查
→ 独立盲测
```

不得通过修改基线数据、隐藏未知状态或改变统计分母来使测试通过。任何数据库迁移必须可重复执行、保留用户现有账本，并提供迁移前后守恒报告。
